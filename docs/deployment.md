# Розгортання staging і production

## Передумови

- Окремі Supabase-проєкти для staging і production.
- Окремі `NEXT_PUBLIC_SUPABASE_URL` та publishable key; service-role key існує лише в секретах Edge Functions.
- Приватний Sites-проєкт із доступом тільки підтверджених власником користувачів.
- У Supabase Auth вимкнені відкрита й анонімна реєстрації, мінімальна довжина пароля — 12 символів, потрібні великі й малі літери, цифри та символи, налаштовані обмеження частоти входів і redirect URL приватного домену.
- Захист від відомих витоків паролів увімкнути після переходу на Supabase Pro; на Free-плані ця функція недоступна.

## Staging

1. Встановити залежності через `npm ci`.
2. Для нового порожнього середовища відтворити схему за перевіреним порядком. Для чинного застосунку застосовувати тільки явний список релізу з `release/2026-10-24/manifest.json`; історичний каталог має розбіжності timestamp і не придатний для сліпого `db push`.
3. Розгорнути Edge Functions: `admin-users`, `file-validate`, `import-preview`.
   Переконатися, що `SUPABASE_SERVICE_ROLE_KEY` доступний тільки цим функціям і ніколи не потрапляє у frontend чи журнал збірки.
4. Запустити `npm run quality` і `npm run db:test` проти ізольованого локального/staging середовища.
5. Виконати ручні сценарії: ролі й MFA, дві вікові команди тренера, призначення тренера воротарів до A/B/C, календар/перенесення, присутність, оплати, блокування форми, дозволи інвентарю, PDF, CSV/XLSX, зашифрована резервна копія.
6. Перевірити, що анонімний користувач, призупинений тренер і тренер іншої групи не отримують дані.

## Production

1. Отримати окреме підтвердження власника на міграцію та публікацію.
2. Створити контрольну резервну копію бази й перевірити процедуру відновлення у staging.
3. Застосувати ту саму перевірену ревізію міграцій і Edge Functions до production.
4. Зібрати застосунок із production-публічними змінними середовища.
5. Опублікувати в чинний приватний Sites-проєкт без розширення аудиторії.
6. Перевірити приватне посилання у ролях адміністратора й тренера, потім зафіксувати час, версію та результати smoke-тесту.

## Відкат

- Не виконувати неперевірений ручний SQL у production.
- У разі помилки повернути попередню версію frontend, заблокувати проблемну операцію та відновлювати дані тільки з перевіреної резервної копії за погодженою процедурою.
- Зміни схеми відкочувати окремою forward-only міграцією; не редагувати вже застосовану production-міграцію.

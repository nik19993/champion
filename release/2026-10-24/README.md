# Оновлення чинного «Клубу Чемпіон» — 24.10.2026

## Статус і межі

Публікацію документів тактики Word/PDF, каталогу 349 завдань у JSON/CSV/SQL та інструкції розгортання у відкритому nik19993/champion власник прямо погодив 24.10.2026. Персональні дані та секрети до пакета не включені. Merge не замінює окремого застосування SQL і публікації frontend.

Це пакет для оновлення існуючого застосунку, не новий проєкт. Перевірений frontend походить із commit cd223fc6775f324d3dfa88c2f7ff7f6a40cc6ed4 приватного тестового source. Базова робоча версія — e7be6d6519db5a5d9f4211a318fe1def242076d7, остання міграція 20260928185734. Резервне копіювання власник відклав; перевіреного повного backup цей пакет не містить.

Merge PR оновлює тільки Git. Автоматичного застосування SQL чи публікації основного сайту в репозиторії не налаштовано. Публікація і міграції виконуються окремо уповноваженим виконавцем. Зберегти чинні адреси Auth та аудиторію сайту. Не переносити конфігурацію, облікові записи або записи тестової БД.

## Склад погоджених змін

- 18 блоків із `docs/proposed-release-2026-10-09.md`: сезони, довнесення даних, профілі/історія/експорт, календар, половини полів, огляд зайнятості, облік тренувань, жовті та клубні картки, пакетна заміна контенту, повідомлення про збереження й стійкість до помилок.
- Автоматичне оновлення зайнятості, без зайвих кнопок, із повідомленням про втрату зв’язку; «Завдання тренера»; позначення року без «р.н.».
- Поточна програма 349 завдань; точні вікові набори U6–U16, воротарські A/B/C; U17 — ручне завдання. Напад, захист і стандартні положення; повний запис «елемент → завдання → пояснення».
- Актуальна тактика у методичних матеріалах, повна заміна матеріалів адміністратором із перевіркою версії; спільний повний словник.
- Переведення гравця тренером між власними групами / адміністратором між будь-якими активними групами; архів без втрати профілю й історії.

## Перед початком

1. Звірити актуальну main, head PR, робочий deployment і журнал БД. Якщо версії змінилися — зупинити застосування й повторити звірку.
2. Виконати read-only `preflight.sql`. Для міграції бронювань потрібні нуль накладок і нуль некоректних ends_at. При конфліктах нічого автоматично не завершувати й не видаляти.
3. Уточнити коротке вікно, коли користувачі не вносять зміни. Зафіксувати лічильники бізнес-таблиць перед/після. Копія SQL/source не є backup даних.
4. Перевірити SHA256 всіх файлів за manifest.json. Потрібен рівно цей список; він не охоплює всі файли supabase/migrations.

## Схема БД

Застосувати 15 schema_steps із manifest.json послідовно. Перші дев’ять — вже перевірені пропозиції з supabase/proposals; наступні шість — доповнення 24 жовтня. Назви файлів і checksum зафіксовані. Кожний крок реєструвати окремою новою міграцією через підтримуваний інструмент; не переписувати історичні 36 записів і не підмінювати їх журналом тестового середовища. Не застосовувати той самий SQL повторно.

Не виконувати `db reset`, `db push` всього каталогу, cleanup_transient_schedule_conflicts, тестові seed або rollback-тести з фіксованими test ID на робочому проєкті. Помилка будь-якого кроку зупиняє наступні; frontend до завершення схеми не публікувати.

## Контент і налаштування

1. Окремо застосувати `approved_curriculum.sql` тільки після всіх schema_steps. Він архівує попередні активні завдання, додає 349 нових і матеріал тактики; не видаляє старих завдань/посилань занять. Повторний запуск відхиляється. Словник із 110 робочих термінів не замінюється вигаданим набором.
2. Початковий сезон адміністратор встановлює явно в «Групах», звіряючи роки народження. Не перейменовувати групи за поточною датою чи не вгадувати когорти автоматично.
3. Для восьми наявних записів майданчиків адміністратор звіряє старі половини та батьківські поля через редагування. Прив’язки не вгадуються за назвою, старі події не видаляються. При накладках прив’язка має відхилятися.
4. Edge Functions admin-users, file-validate, import-preview використовувати з цієї ревізії; серверні секрети залишаються тільки на сервері. Звірити фактично розгорнуті версії перед deploy; незмінні функції не перевипускати без потреби.

## Frontend і публікація

1. Встановити Node.js >=22.13, `npm ci`; запустити lint, typecheck, npm test. Для відтворення інтеграційного SQL-тесту потрібна pinned @electric-sql/pglite 0.5.11: `node scripts/verify-release-integration.mjs /absolute/path/to/pglite/dist/index.js`.
2. Додати через захищені налаштування тільки browser-safe змінні з `.env.production.example`, з реальними робочими значеннями. APP_ENV=production. Не копіювати .env.local тестової версії.
3. Перевірити env, виконати build; у збірці має бути робочий Supabase host, а не тестовий. service_role, secret key і DB-пароль у frontend заборонені.
4. Опублікувати чинний сайт з наявною аудиторією; не створювати новий сайт замість нього. Зберегти точний deployment/version/commit.

## Контроль після оновлення

Звірити кількість гравців, груп, занять, присутностей, результатів, оплат і файлів із початковими лічильниками. Зміна кількості активних завдань очікувана; їх історичні рядки зберігаються. Перевірити звичайний admin login з MFA і coach login без обов’язкового MFA; reload/logout/login; відкриття кожного розділу; відображення історичних даних; календар/половини; словник/програму; PDF; переведення та архів на окремих погоджених тестових записах, не на реальних дітях навмання. Записати результати й обмеження перевірок.

При помилці зупинити проблемні операції, повернути попередній frontend за потреби. Не очищати БД і не виконувати неперевірений зворотний SQL. Схему виправляти окремою погодженою forward-міграцією. Без backup повне відновлення даних не гарантоване.

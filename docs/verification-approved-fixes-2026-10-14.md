# Перевірка п’яти погоджених виправлень — 14.10.2026

## Поведінка

1. **Сезон.** Актуальний `display_age` визначає навчальні завдання, структуру
   тренування та віковий набір імпорту; до ініціалізації діє `age`.
   Серверні правила для призначеного віку, реєстрації й прикріплення матеріалів
   використовують той самий вік. Воротарські групи залишаються без спільного
   штучного віку. Історичні матеріали доступні через призначену групу події.
   Конфлікти бронювання показують `display_code` із запасним `code`.
   Реєстрація документа й читання результату виконуються окремо: чинний
   STABLE RLS helper не бачить новий запис у власному `INSERT RETURNING`.
   Невдала реєстрація прибирає завантажений файл; перевірка файла залишається.
2. **Сесія.** Підтвердження обов’язкової зміни пароля прив’язане до ID користувача.
   Logout або інший обліковий запис скидає його; оновлення токена того самого
   користувача зберігає стан. Пізня відповідь попередньої сесії не замінює нову.
   Адміністраторський MFA та вхід тренера без обов’язкового MFA збережені.
3. **Збереження.** Інвентар тренера/адміністратора, статус і коментар форми,
   а також скасування останньої зміни перевіряють повернений ID.
   Помилка, `null` або інший ID не позначаються як «Збережено»; введення зберігається.
4. **Типи БД.** Додано таблиці сезону, три колонки групи, п’ять RPC профілю/сезону
   і тип уже наявного RPC реєстрації фото. Повна ізольована схема звірена
   з Row/Insert/Update, nullable колонками, іменами й аргументами всіх RPC.
   `task_usage` залишається view. Первинні ключі експорту звірені з БД.
5. **Адміністративний JSON.** Усі 46 робочих таблиць, stable PK pagination,
   фактичні довжини сторінок, exact counts, виявлення повторів/обриву та фінальна
   перевірка кількостей. Активний адміністратор/MFA перевіряються до й після.
   AES-256-GCM збережено. Невдача не створює файл або запис успішного експорту.
   Це дані застосунку, не повний backup PostgreSQL/Auth/Storage.

## Перевірка

`npm run quality`: ESLint, TypeScript, Node tests та production static build.
SQL перевірено тільки в локальному PGlite з вигаданими обліковими записами:
36 звірених історичних source-файлів і шість SQL-пропозицій, 46 RLS таблиць.
Окремі fixtures перевіряють сезон/імпорт/профіль, бронювання та облік тренування.
Браузерні fixtures перевіряють профіль/PDF, календар/мобільну форму,
бронювання, облік, ізоляцію сесій, підтвердження запису й відмову неповного backup.

Результат: 120 Node tests, 160 браузерних перевірок (48 профіль, 27 календар,
22 бронювання, 27 облік, 36 стабілізація), 114 перевірок окремих SQL fixtures
(38/48/28) і 1602 assertions повної схеми/типів/ключів та синтетичних workflows.
Останній показник містить багато перевірок окремих колонок, а не 1602 окремі
користувацькі сценарії. Усі команди завершилися успішно.

```bash
npm run quality
node scripts/verify-proposals.mjs /path/to/pglite/dist/index.js
node scripts/verify-venue-bookings.mjs /path/to/pglite/dist/index.js
node scripts/verify-training-register.mjs /path/to/pglite/dist/index.js
node scripts/verify-release-integration.mjs /path/to/pglite/dist/index.js
node scripts/verify-readiness-ui.mjs /path/to/esbuild/lib/main.js /path/to/playwright/index.mjs /path/to/chromium
```

Інші браузерні команди: `verify-profile-export-ui.mjs`, `verify-calendar-ui.mjs`,
`verify-venue-booking-ui.mjs`, `verify-training-register-ui.mjs`, з тими ж аргументами.
PGlite/esbuild/Playwright можна встановити в окремий тестовий каталог;
виробничі залежності цього виправлення не змінені.

## Випуск

Усі нові SQL залишаються в `supabase/proposals`, включно з
`20261014071648_season_effective_age_access.sql`. Вони мають застосовуватися
в порядку імен після звіреної базової схеми лише під час окремо погодженого
випуску. Шоста пропозиція залежить від першої (колонки сезону).
Змінені правила бронювання також потребують першої пропозиції.
Не застосовувати заборонений cleanup конфліктів, не ремонтувати ledger
і не запускати `db push` усіх історичних файлів із різними timestamps.

Ця перевірка не змінює чинного середовища. Для готовності до production ще
потрібні захищений актуальний PostgreSQL/Auth/Storage backup, контрольне
відновлення в окремому середовищі, вхід через справжній Auth service й перевірка
одночасного бронювання через незалежні PostgreSQL-сесії. PGlite має синтетичні
Auth/Storage таблиці та не замінює ці перевірки. Merge/deploy не виконані.
